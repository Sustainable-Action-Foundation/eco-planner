# Workflow conventions

## Tooling
- `yarn`, never `npm` or `npx`. `yarn lint` runs `tsc` and ESLint; `yarn dev` runs lint alongside the dev server.
- This Next.js version differs from older ones. Read the bundled docs in `node_modules/next/dist/docs/` before writing framework code (`AGENTS.md`, regenerated by `next dev`, says the same).

## Branches
- `dev` is the integration branch and runs ahead of `main`. Pushes to `dev` deploy to staging (reseeded each time); pushes to `main` deploy to production behind a required review. CI runs the tests on both (`.github/workflows/build-and-publish.yaml`). Pull request runs only test (the test stack builds both images); the images are built again and pushed on pushes to `dev` and `main`.
- Real features, schema changes and anything that may sit unmerged get a git worktree with a normally named branch, created from **local `dev`**: `git worktree add -b <name> .claude/worktrees/<name> dev`. Tools that create worktrees for you may default to `origin/main`, which is far behind; and branching from `origin/dev` sets an upstream you then have to unset.
- In a fresh worktree: symlink the main checkout's `.env` (unless the work needs a different database), then `yarn install` and `yarn prisma generate`. Without the generated client `yarn lint` fails.
- Tiny, low-risk tweaks (a few lines, a locale key, a spacing fix) go straight onto `dev` as a plain commit. A worktree round trip is pure overhead for those. When unsure, ask.
- Coding agents commit but never push.

## Commits
- Plain `git commit` with the configured identity. Never override `user.name`, `user.email` or `--author`: commits are signed, and an identity that does not match the key shows as unverified.
- Messages are short (2–15 words), lowercase first letter, not verbose.
- A PR that resolves an issue says `Closes #N`.

## Versioning
- The version in `package.json` is deliberately not semver: an informal patch bump in its own commit, usually before a PR to `main`. `.github/workflows/version-check.yaml` fails a PR into `main` that does not bump it.
- Do not try to make the version string more meaningful. Granularity comes from git instead: the build appends the number of commits since the last bump (`0.17.4+6`), computed by `scripts/checkCommitsAhead.ts` and shown on `/info` with the commit hash. CI passes the count in because docker builds see a shallow checkout.

## Code conventions that are easy to miss
- Enum-ish constants: PascalCase const, PascalCase keys, UPPER_SNAKE values, with a same-named type exported next to it. Enforced by a local ESLint rule (`scripts/eslint/enumStyle.ts`).
- Before adding a UI component, look at the generic ones (`src/components/generic/`, see [`README.md`](../../README.md#components)).
- Translation keys are literal; see [i18n.md](i18n.md).

## Project board
- Planning lives on the organisation's GitHub project board. Check for a matching card or issue when starting something, and move cards when work lands.
- **Never add or change the options of a single-select field (such as Status) through the GraphQL API** (`updateProjectV2Field`). The mutation replaces the option list wholesale: options get new ids and every item's current value is silently cleared. Add columns in the board UI, then read the new option id.
- Setting an item's field value and reordering items through the API are safe.
- Before any field-level mutation, dump the items so statuses can be rebuilt.
